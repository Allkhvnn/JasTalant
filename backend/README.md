# JasTalant Backend

CRM для футбольных академий Казахстана. Java 21, Spring Boot, Gradle,
PostgreSQL, Spring Data JPA, Flyway, Spring Security.

## Требования

- JDK 21; `JAVA_HOME` должен указывать на его каталог.
- Docker Desktop с запущенным Linux Engine — для локальной БД и тестов.
- Gradle устанавливать отдельно не требуется: используйте Wrapper.

## Локальный запуск (PowerShell)

Команды выполняются из каталога `backend`.

```powershell
$env:JAVA_HOME = 'C:\Program Files\Eclipse Adoptium\jdk-21.0.9.10-hotspot'
$env:Path = "$env:JAVA_HOME\bin;$env:Path"
java -version

$env:DB_PASSWORD = 'your-local-password'
$jwtKey = New-Object byte[] 32
$rng = [System.Security.Cryptography.RandomNumberGenerator]::Create()
$rng.GetBytes($jwtKey)
$rng.Dispose()
$env:JWT_SECRET_BASE64 = [Convert]::ToBase64String($jwtKey)
docker compose up -d --wait
.\gradlew.bat bootRun --args='--spring.profiles.active=local'
```

Путь JDK замените на свой. Пароль выберите самостоятельно. Приложение слушает
порт 8080; PostgreSQL доступна только через localhost:5432.
Mailpit принимает локальные письма на порту 1025; посмотреть коды подтверждения
можно в браузере по адресу http://localhost:8025. Письма не уходят реальным адресатам.
JWT-ключ храните вне репозитория и используйте один и тот же при перезапусках;
генерация нового ключа делает ранее выданные токены недействительными.
При конфликте порта измените порт Compose и задайте соответствующий `DB_URL`.

Compose также читает `.env`, созданный по образцу `.env.example`, но Spring Boot
не загружает этот файл автоматически: передавайте `DB_PASSWORD` приложению через
окружение или настройки запуска IDE. Не коммитьте пароли.
Пароль PostgreSQL задаётся при первом создании тома; изменение переменной
не меняет пароль в уже существующей БД.

Остановка БД с сохранением данных: `docker compose down`.

## Сборка и тесты

```powershell
.\gradlew.bat build
```

Тест поднимает отдельный временный PostgreSQL через Testcontainers и проверяет
загрузку Spring-контекста, подключение и таблицу истории Flyway. Локальная БД
Compose для этого не нужна. Docker обязателен: при его отсутствии тест падает,
а не пропускается. Тестовый профиль не задаёт подключение к рабочей БД.

Для проверки только компиляции и упаковки: `.\gradlew.bat assemble testClasses`.
Эта команда **не запускает тесты**.

## Конфигурация

Профиль `local` использует `DB_URL` (по умолчанию
`jdbc:postgresql://localhost:5432/jastalant`), `DB_USERNAME` (по умолчанию
`jastalant`) и обязательный `DB_PASSWORD`.
Без профиля `local` передавайте стандартные `SPRING_DATASOURCE_URL`,
`SPRING_DATASOURCE_USERNAME`, `SPRING_DATASOURCE_PASSWORD`.

Flyway управляет схемой, Hibernate работает в режиме `validate`.
Миграция V1 создаёт академии, пользователей и членство. Open Session in View отключён, JDBC использует UTC.
Compose предназначен только для локальной разработки, не для production.

## Модель и границы доступа

Используем общую БД и схему. Добавлена основа модели:
`Academy`, `User`, `AcademyMembership` (роль пользователя в академии).
JWT удостоверяет пользователя. Для GET /api/academies/{id} сервер проверяет
актуальное членство в указанной академии по БД; один ID не даёт доступа.
Роли платформы также читаются из БД при каждом запросе, а не из присланных claims.

Все операции и связи между данными должны учитывать академию; это необходимо
проверять интеграционными тестами доступа между двумя академиями. Дополнительная
защита RLS потребует отдельной роли БД без обхода политик и передачи контекста
академии в пределах транзакции.

Пользователь имеет глобально уникальный email (нормализуется в нижний регистр).
В каждой академии у него набор ролей: ADMIN, COACH и/или PARENT. Роли хранятся
в `academy_membership_roles`, членство остаётся уникальным для пары академия/пользователь.
Членство можно временно отключить без удаления истории; отключённая академия
не возвращается пользователю и не проходит проверку AcademyPermissionService.
На уровне платформы `User.platformRole` имеет значение USER (обычный пользователь,
без дополнительных прав) или SUPER_ADMIN (владелец платформы).
V2 переносит существующие роли ADMIN/COACH и не повышает права пользователей.
Публичного механизма назначения SUPER_ADMIN нет; владелец создаётся отдельным
запуском с профилем bootstrap-admin (см. docs/onboarding.md). Пароли хешируются
PBKDF2 с индивидуальной солью; открытые пароли не сохраняются.
Репозиторий членства читает данные с обязательным academy_id, но сам по себе
не проверяет права вызывающего: AcademyPermissionService проверяет академию и роли,
GroupService и PlayerService — доступ к конкретным группам и игрокам.
Тесты проверяют миграцию, JPA, разные роли в двух академиях, выборки по академии,
уникальность email/членства, допустимые роли и внешний ключ академии.

Также проверяются несколько ролей в одном членстве, разделение платформенных
и академических ролей и обновление БД с данными V1 до V2.
Набор ролей в Java должен быть непустым; обычные внешние ключи таблицы ролей
не запрещают пустое членство при прямой записи SQL.

ADMIN управляет группами и игроками своей академии; COACH видит только назначенные
группы и их игроков. Для PARENT общий доступ закрыт: он видит только игроков из
подтверждённой связи родитель/ребёнок. ADMIN и назначенный COACH могут вести
посещаемость доступных им групп; PARENT читает историю посещаемости только своих
связанных детей.
Несколько ролей дают совокупность разрешений.

Реализованы регистрация заявки, подтверждение email, JWT-вход с refresh-сессией,
восстановление пароля, просмотр своей
заявки, одобрение/отклонение владельцем платформы и чтение своей академии.
