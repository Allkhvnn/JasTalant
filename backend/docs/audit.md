# История действий

Журнал хранит успешные бизнес-действия с момента применения Flyway V14.
События прошлого не восстанавливаются. Запись создаётся в той же транзакции,
что и изменение: отказ в доступе, ошибка валидации, устаревшая версия или откат
не оставляют запись об успешном действии. Если запись истории не сохранилась,
бизнес-изменение также откатывается.

## Доступ

- ADMIN читает историю только своей активной академии с действующим членством.
- COACH и PARENT не имеют доступа к журналу и списку авторов.
- SUPER_ADMIN читает журнал управления платформой. По существующей политике
  AcademyPermissionService он также может запросить журнал конкретной академии.
- Разделение академий задаётся сервером по academyId из URL после проверки доступа.
  Фильтр по автору не расширяет область видимости.

Страница администратора: `/academy/{academyId}/audit`, пункт «История действий»
в меню академии. Страница владельца: `/platform/audit`, пункт в верхнем меню.
Интерфейс RU/KK/EN; дата и время отображаются в часовом поясе браузера.

## API только для чтения

```text
GET /api/academies/{academyId}/audit
GET /api/academies/{academyId}/audit/actors
GET /api/platform/audit
GET /api/platform/audit/actors
```

Параметры списка: `page` (с 0), `size` (1–100, по умолчанию 20),
`action` (AuditAction), `actorId` (UUID), `from`, `until` (ISO-8601 Instant).
Начало включительно, конец исключительно. При заданных обеих границах
`from` должен быть раньше `until`. UI переводит выбранные календарные дни
в границы локального часового пояса; день «по дату» включён полностью.

```text
GET /api/academies/{academyId}/audit?action=PLAYER_UPDATED&page=0&size=20
GET /api/platform/audit?from=2026-10-01T00:00:00Z&until=2026-11-01T00:00:00Z
```

Ответ: `{items, page, size, totalElements}`. Запись содержит `id`, `academyId`
(null для платформы), `actorId`, снимок `actorName`, `action`, `targetId`,
снимок `targetName`, `occurredAt`. Сортировка: `occurredAt DESC, id DESC`.
Список авторов содержит `{id, name}` только из событий соответствующей области;
для переименованного автора берётся имя из его последнего события.

## Какие события записываются

| Область | События |
|---|---|
| Игроки | PLAYER_CREATED, PLAYER_UPDATED, PLAYER_DELETED |
| Фото игроков | PLAYER_AVATAR_UPDATED, PLAYER_AVATAR_REMOVED |
| Импорт | PLAYERS_IMPORTED — одна запись с количеством импортированных игроков |
| Посещаемость | ATTENDANCE_CREATED, ATTENDANCE_UPDATED — одна запись на сохранённую ведомость |
| Развитие | DEVELOPMENT_CREATED, DEVELOPMENT_UPDATED, DEVELOPMENT_DELETED |
| Участники | MEMBER_PROFILE_UPDATED, MEMBER_ROLES_UPDATED, MEMBER_ACCESS_ENABLED, MEMBER_ACCESS_DISABLED |
| Фото участников | MEMBER_AVATAR_UPDATED, MEMBER_AVATAR_REMOVED |
| Заявки | APPLICATION_APPROVED, APPLICATION_REJECTED — журнал платформы |
| Академии | ACADEMY_ACTIVATED, ACADEMY_SUSPENDED, ACADEMY_ARCHIVED — журнал платформы |

Изменение участника может дать несколько событий (например, роли и отключение
доступа). Неизменённые роли/имя/активность не создают событий, повторная установка
того же статуса академии также не создаёт событие. Предпросмотр импорта и импорт
с ошибками не записываются. Успешный импорт не создаёт тысячи отдельных событий
PLAYER_CREATED. Скачивание шаблона, чтение и экспорт не входят в первую версию.

Посещаемость хранит название группы и дату, оценка развития — имя игрока и дату.
Это журнал действий, без старых/новых значений каждой ячейки. Пароли, JWT, коды,
телефоны и email родителей, фотографии, комментарии, причины отказа/блокировки,
тела запросов и писем не копируются. Создание групп, расписание, приглашения,
связи родителей, входы и повторная подача заявки пока не журналируются.

## Хранение и проверка

`audit_events` — отдельная JPA-сущность с `@Immutable`, запись через AuditWriter
с обязательной существующей транзакцией. Публичных API создания, редактирования
и удаления нет. Имена и ID — снимки без внешних ключей, поэтому удаление игрока
или учётной записи не удаляет историю. Журнал не является защитой от изменений
оператором с прямым административным доступом к БД. Автоматической очистки нет.

После перезапуска backend применится миграция V14. Создайте и измените игрока,
отметьте посещаемость тренером, затем откройте журнал администратором. Проверьте
фильтры и три языка. Владелец увидит новые решения по заявкам и смену статусов
академий в своём журнале. Старые записи до миграции в него не добавляются.

Интеграционные тесты AuditLogTests используют отдельную PostgreSQL и подменённую
почту: изоляция академий, актуальные права, фильтры и границы дат, пагинация,
откаты, сохранение снимков после удаления, импорт, события сотрудников и платформы,
отсутствие API для подделки/изменения записей.
