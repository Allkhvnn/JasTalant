# Архитектура backend

Проект организован по функциональным модулям, внутри них — по слоям Spring Boot.
Общий базовый пакет: `kz.jastalant.backend`.

```text
backend
├── config               # Spring Security, JWT/PasswordEncoder/Clock beans
├── security             # выпуск JWT
├── common
│   ├── dto              # ответы с пагинацией
│   ├── exception        # бизнес-ошибки и единый HTTP-обработчик
│   └── service          # проверка параметров пагинации
├── auth
│   ├── bootstrap        # отдельный запуск создания владельца
│   ├── controller
│   ├── dto
│   ├── mapper
│   └── service
├── academy
├── onboarding           # заявки на подключение, прежний пакет application
├── invitation           # приглашения COACH/PARENT и их принятие
├── group
├── player
├── attendance           # ведомости группы и отметки игроков
├── parent               # подтверждённые связи родитель/игрок
├── membership           # членство, роли и список участников академии
└── user                 # пока entity и repository
```

В модулях academy/onboarding/invitation/group/player/attendance/parent используются `controller`, `dto`,
`entity`, `repository`, `service`, `mapper`. Пустые слои не создаются заранее.

## Ответственность слоёв

- Controller разбирает HTTP-запрос, запускает Bean Validation и передаёт ID
  пользователя из проверенного JWT в сервис. Не обращается к репозиториям.
- Service реализует сценарий, определяет транзакцию, проверяет права и вызывает
  репозитории. Возвращает DTO внешнему слою; внутренние методы могут работать с сущностями.
- Repository выполняет операции JPA. Для групп/игроков выборки ограничены academyId.
  Принудительная запись изменений также выполняется через repository.flush(),
  чтобы Spring переводил ошибки Hibernate в DataAccessException.
- Entity описывает состояние и изменения объекта. Не зависит от DTO, контроллеров,
  сервисов, репозиториев и мапперов. Например, Player принимает значения полей,
  а не PlayerRequest. JPA и Bean Validation разрешены; защитные JsonIgnore у User
  сохранены, но HTTP-контроллеры всё равно никогда не возвращают User.
- DTO задаёт контракт API, включая ограничения входных данных. Формат прежних
  ответов регистрации/заявок сохранён после перемещения классов.
- Mapper преобразует сущности и DTO, не обращаясь к БД. Небольшие мапперы написаны
  явно, без дополнительного генератора кода.

BusinessException содержит код ошибки без HTTP-зависимостей. ApiErrors переводит
его в ProblemDetail и HTTP-статус; там же обрабатываются конфликты БД и версий.
Перемещение пакетов не меняет имена таблиц; существующие миграции не переписываются.

## Доступ и транзакции

AcademyPermissionService — единое место проверки подтверждения email, текущего
членства, роли ADMIN/COACH и полномочий SUPER_ADMIN. GroupService дополнительно
проверяет назначение тренера на конкретную группу, PlayerService использует ту же
проверку для игроков. Данные родительского контакта не являются правом доступа.
ParentPlayerService разрешает родителю читать только игроков из таблицы
parent_players. InvitationService выдаёт только роли COACH/PARENT и создаёт эти
связи после принятия приглашения. AttendanceService повторно использует проверку
видимости группы, поэтому тренер работает только со своими назначениями.

Изменяющие сценарии выполняются с `@Transactional`, чтение — с `readOnly=true`.
Составные внешние ключи V4–V6 запрещают связи между академиями даже при прямой
записи SQL. RLS пока не реализован; это ограничение целостности плюс проверки
сервисов. Версии группы, игрока и ведомости защищают изменения от перезаписи
устаревшим клиентом.

Интерфейсы Service/ServiceImpl не дублируют каждый класс: их стоит вводить, когда
появится отдельный контракт или несколько реализаций. Слои не добавляются ради
пустых файлов.

Проверка: `gradlew.bat build`. Интеграционные тесты используют PostgreSQL и JWT,
проверяют подключение академий, группы, игроков, приглашения и посещаемость.
